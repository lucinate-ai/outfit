# Plan: move endpoint access onto Tailscale

**Status: proposed, not implemented.** The stack currently exposes vLLM on a
public Elastic IP, restricted to a single CIDR (`allowedCidr`) with the API
key as a second layer. This works, but the IP allowlist needs updating every
time the home IP changes, and traffic is plain HTTP, so the API key is
visible in transit. Joining the instance to a tailnet fixes both.

## Target design

The instance runs `tailscaled` and joins the tailnet at first boot. Clients
reach vLLM at its MagicDNS name (`http://cloud-vm-llm:8000/v1`) instead of a
public IP. Tailscale only makes outbound connections, so:

- The security group loses its port-8000 ingress rule — nothing is publicly
  reachable at all, and `allowedCidr` stops existing as a concept.
- All traffic rides inside WireGuard, so the API key is no longer visible on
  the wire. Keep vLLM's `--api-key` anyway as defence in depth.
- The Elastic IP becomes redundant (MagicDNS is the stable name) and can be
  dropped, saving ~$3.60/month.

The scale-to-zero machinery is untouched: the Lambdas reach the instance via
SSM and the EC2 API, not the network path, so wake, idle-stop and status all
work as they do today. The instance is stateless — terminated when idle, a
fresh root from the AMI on each wake — so there is no persisted Tailscale
state: each wake registers as a new node via the reusable, pre-authorised auth
key, and the previous node lingers in the admin console until cleaned up (see
caveats).

## Changes required

1. **Tailscale auth key** — a new Secrets Manager secret. Unlike the API key
   it cannot be generated by the stack: it comes from the Tailscale admin
   console (see one-time setup below) and is passed in as a context value or
   pasted into the secret after deploy. Read once by user-data at first boot.
2. **`lib/llm-stack.ts`**
   - Add the auth key secret and grant the instance role read on it.
   - Remove the SG ingress rule and the `CfnEIP`/association (or gate both
     behind a `tailscaleEnabled` config flag during the transition).
   - `BaseUrl` output (and the Lambdas' `BASE_URL` env) becomes
     `http://<tailscaleHostname>:8000/v1`.
3. **User-data** (`buildUserData` in `lambda/start/index.ts`)
   - Install tailscaled (`curl -fsSL https://tailscale.com/install.sh | sh`
     or the apt repo directly, pinned).
   - `tailscale up --authkey "$TS_AUTHKEY" --hostname cloud-vm-llm` before
     starting the vLLM service.
4. **`lib/config.ts`** — add `tailscaleHostname` (default `cloud-vm-llm`);
   make `allowedCidr` optional (only required if the public path is kept as
   an escape hatch).
5. **README** — deploy walkthrough gains the one-time Tailscale setup; the
   security notes and cost table are updated (EIP line goes away).
6. **outfit** — no code change. `outfit remote start` prints whatever
   `base_url` the start Lambda returns, which now carries the MagicDNS URL.

## One-time setup (manual, in the Tailscale admin console)

- Create a tag for the node, e.g. `tag:llm`, owned by your user. Tagged
  devices are treated as servers: their node keys don't expire, which is what
  a stop/start instance needs.
- Create a **pre-authorised, reusable** auth key with `tag:llm`. (Not
  ephemeral — ephemeral nodes are removed when they go offline, and this
  instance is offline whenever it's stopped.)
- Add an ACL rule allowing your devices to reach `tag:llm:8000`.

## Verification

Deploy, then from a tailnet device: `tailscale status` shows the node;
`curl http://cloud-vm-llm:8000/v1/models -H "Authorization: Bearer $OPENAI_API_KEY"`
works; the same curl against the old public IP fails (port closed). Stop and
wake the instance and confirm the node comes back with the same name.

## Caveats

- Home-to-EC2 connections normally go direct over WireGuard; when NAT
  traversal fails Tailscale falls back to a DERP relay, which is noticeably
  slower for token streaming. Rare, but check `tailscale status` for
  `relay` if generation feels sluggish.
- The auth key is only consumed at first boot. If the instance is ever
  replaced (user-data or AMI change), the replacement re-registers — the old
  node lingers in the admin console until removed, and a reusable key makes
  re-registration automatic. Rotate the key like any other credential.
- Free personal Tailscale plan covers this (well under the device limit).

## Rollback

Everything is additive: re-enable the SG ingress rule and EIP, point
`BaseUrl` back at the public address, redeploy. The tailnet node can stay —
it does no harm alongside the public path.
